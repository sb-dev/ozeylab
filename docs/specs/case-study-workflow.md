Version 1.2 · 8 October 2026

Use this workflow to decide how to pursue a project or opportunity. It compares complete business alternatives, estimates the money and work each could require, and recommends one route. It accepts a domain name, an idea or project description, specification files, or any combination.

The output is one case study. It includes a recommendation, one credible alternative, financial scenarios, and a costed specification for the selected project's bootstrap. Here, **bootstrap means the initial GitHub repository used to start the project**. Its structure, instructions, specifications and starting assets depend on the operating model. For commercial projects, work and funding through the first commercial outcome belong in a commercial launch specification. An explicitly noncommercial project uses a launch specification for its intended operational outcome.

Generating the case study specifies the repository. Executing the bootstrap creates and verifies it.

## 1 Inputs and defaults

Provide at least one starting input: a domain name, an idea or project description, or specification files. Use information already supplied before asking questions. A domain is optional when other material defines the project.

| Input | How to use it |
| --- | --- |
| Domain name, when supplied | Record the exact name. Establish whether ownership is reported or verified. |
| Idea or project description | Capture the intended outcome, audience, context and proposed approach. |
| Specification files | Preserve the supplied versions and origins. Extract requirements, assumptions, dependencies, decisions and open questions. Record conflicts or extraction limitations. |
| Optional direction | Treat it as a hypothesis unless the user makes it a firm constraint. Explore credible alternatives within firm requirements. |
| Objective | Record whether the priority is sale proceeds, operating income, limited owner work, long term business value, growth of an existing business, or an explicitly noncommercial outcome. |
| Constraints | Record available cash, maximum acceptable loss, owner hours, deadline, geography and excluded activities when known. |
| Existing assets | Record traffic, revenue, offers, content, code, audience, customer relationships, expertise and delivery capacity. |
| Optional repository context | Existing or intended GitHub repository, reusable starting assets and applicable instructions or skills. Repository details are not required to evaluate a project; resolve the destination and visibility when creating it. |
| Reporting basis | Default to GBP and comparisons at 90 days, 12 months and 36 months. State these as analytical defaults. Choose the customer market from evidence, not the reporting currency. |

If cash or time limits are missing, report the requirements and make the recommendation conditional on them. Do not invent the user's budget or available hours. Ask at most two focused questions when the answers could change the preferred route. Continue independent research while those facts remain unknown.

The default objective is to compare net financial benefit after allowing for owner time. Show tradeoffs where rapid cash, lower risk and larger long term gains lead to different choices.

For an explicitly noncommercial objective, assess intended users, outcome, delivery, distribution, cost, funding and capacity. Apply commercial-only requirements below when a revenue or sale route is being assessed. Quantify income or savings only where a credible mechanism exists. Use `docs/launch-spec.md` for the first useful operational outcome.

## 2 Workflow

| Stage | Work | Required result |
| --- | --- | --- |
| 1 Establish the starting position | Inspect all supplied inputs, assets, requirements, constraints and optional direction. | A factual brief with assumptions labelled. |
| 2 Explore commercial possibilities | Check all operating families and credible alternative approaches to the opportunity. | A coverage table and distinct candidate strategies. |
| 3 Research and screen | Check the claims that could make each candidate viable or unsuitable. | Evidence, exclusion reasons and unresolved questions. |
| 4 Design complete alternatives | Define delivery, development, marketing, funding and ownership for the strongest candidates. | Comparable candidate profiles. |
| 5 Model the money | Calculate cash, owner effort, funding needs and conditional sale outcomes. | Scenarios on the same basis and time horizons. |
| 6 Challenge the comparison | Test weak assumptions, missing costs and favourable treatment of a preferred idea. | Corrected models and thresholds that change the decision. |
| 7 Recommend | Select one route and explain when one alternative becomes preferable. | A decision with evidence and conditions. |
| 8 Define the repository bootstrap | Specify the initial GitHub repository for the selected operating model and how to create it. | Repository contents, staged bootstrap process, launch specification and acceptance checks. |

Revisit the relevant stage when new evidence changes a decision. A price change usually returns to the financial model. A different buyer returns to option design. A failed demand assumption returns to exploration.

## 3 Establish the starting position

Build one starting brief from the supplied inputs. Record the requested outcome, existing context, firm requirements, proposed approaches, assets, assumptions and unknowns. Preserve the origin and revision of supplied specifications. Treat their statements about demand, costs or valuation as claims to assess.

Resolve overlapping inputs without silently discarding conflicts. A user-approved requirement constrains the options; a draft design remains open to challenge. Distinguish specified, implemented and observed capabilities.

### Domain assessment when supplied

Assess the domain as both an asset and a possible business identity.

Check its meaning, spelling, pronunciation, extension, likely languages and plausible audiences. Inspect existing use, relevant history, renewal cost and current offers when accessible. Use available analytics for traffic claims. Separate third party estimates from first party records.

Check name conflicts, transferable rights and access restrictions where they could prevent the proposed use or sale. Do not treat a public search as proof of legal clearance. Focus specialist work on actual issues that affect a candidate.

Record what advantage this particular domain could provide. That might be recognition, a useful name, existing traffic or a fit with an existing offer. The name alone does not establish demand, search performance or buyer willingness to pay.

### Baseline and existing projects

Choose a baseline that represents the actual starting position: no new commitment, continuing the current approach, or an available asset sale.

When an owned domain is part of the decision, include a domain sale baseline. Also examine holding, leasing or releasing it where relevant. A quoted asking price is not an available cash offer. If no buyer is known, model both sale and no sale. Do not invent a domain asset for a description-only or specifications-only case.

For an existing business or project, compare the proposed change with continuing the current approach. Count only incremental future costs and gains, identify displaced sales or work, and preserve the current project's established requirements.

## 4 Explore the full commercial space

### Operating families

Screen every family below. Record a plausible candidate or a brief reason that the family does not fit. Add a family if a credible possibility falls outside this map.

| Family | Models to consider where relevant |
| --- | --- |
| Assets and rights | Domain sale or lease; brand and website package; project or code sale; content and intellectual property licences; commissioned launch assets. |
| Delivered services | Professional services; fixed scope services; creative production; managed operations; back office processing; compliance support; managed cybersecurity; local services; events; delivery through partners. |
| Tools and software | Subscription software; usage based tools; APIs; plugins; downloadable software; consumer apps and games; licensed or white label products. |
| Information and access | Data and intelligence; research; publishing; newsletters; communities; education; courses; digital products; advertising and sponsorship. |
| Matching and transactions | Lead generation; affiliate referrals; directories; recruitment; brokerage; marketplaces; transaction facilitation. |
| Goods and fulfilment | Retail; resale; specialist physical products; subscriptions and replenishment; manufacturing; rental and equipment access. |

These are search headings, not a required set of businesses to build. The nine categories in the supplied OS fit within them. For example, creative services, back office processing and managed compliance remain distinct service candidates when their buyers, responsibilities or economics differ.

### Separate the design choices

Describe each candidate through the following dimensions. Combine compatible choices into one complete strategy.

| Dimension | Question |
| --- | --- |
| Customer and outcome | Who pays, who uses it, and what useful result do they obtain? |
| Operating model | What does the business deliver and what recurring work must it perform? |
| Revenue mechanism | Is payment a sale, project fee, subscription, usage fee, commission, referral fee, sponsorship, advertising payment or licence? |
| Domain role, when present | Is the name the asset, the business identity, an acquisition channel or an asset supporting an existing business? |
| Development method | What is transferred, created, bought, licensed, configured, commissioned or built? |
| Delivery method | Which tasks use people, existing tools, ordinary software or AI? |
| Marketing and sales | Where do paying customers come from and how do they buy? |
| Funding and ownership | Who pays for the launch, who owns the assets, and who receives the proceeds? |
| Intended outcome | Is the aim to sell, license, operate for income, support an existing business or build for a later sale? |

Selling an operating business is an exit choice. Its underlying operation could be software, services, information or physical commerce. A funding method or advertising channel is usually a configuration choice, not a separate business model.

### Generate distinct candidates

Create candidates with materially different buyers, paid outcomes, operations, ownership or sources of profit. Two versions of the same landing page are one candidate. A brand package sold to an agency and an enquiry business operated by the owner are separate candidates.

Explore the supplied direction properly. Include credible strategies that challenge its assumptions while respecting firm requirements. A domain, description or detailed software specification does not by itself make a software business preferable to a service, publication or sale package.

Generate only combinations with a commercial reason to exist. Stop expanding when the families are covered and additional combinations repeat the same economics or fail known constraints.

Retain the sale baseline and normally develop three to five serious alternatives. Use fewer when evidence supports fewer. Apply comparable research effort to the candidates that could realistically win.

## 5 Research and screen the candidates

### Evidence record

Keep one evidence table inside the case study. Link each decision critical number or claim to its source or assumption.

| Field | Required content |
| --- | --- |
| Claim or input | The exact fact, quantity or proposition being used. |
| Basis | Source link or record, date, geography, measurement period and relevant definition. |
| Status | Observed, reported, assumed, calculated, unknown or contradicted. |
| Consequence | What changes in the recommendation if the claim is wrong? |
| Next evidence | The least expensive useful check and its required result. |

Observed means directly inspected or measured, with the method stated. Reported means a user or source asserts it. Assumed means a planning input. Calculated means derived from identified inputs. Calculations retain the uncertainty of those inputs. Unknown is not zero. Contradicted claims must be corrected or removed from the model.

A verified calculation does not verify its assumptions. Several articles repeating the same original claim count as one source. Keep the confidence of demand, delivery, acquisition, costs and exit assumptions separate.

### Questions that affect the decision

For each serious candidate, establish:

1. What event makes the buyer act, who controls the budget, and what the buyer does now.

2. What competing paid offers, free alternatives or internal processes already exist.

3. Which buyers can actually be reached through the proposed channel.

4. What the business must deliver, including exceptions, revisions, support and ongoing work.

5. Which people, data, permissions, suppliers or platforms the model depends on.

6. What evidence supports the price, demand, delivery cost and time to a sale.

Use current primary sources for rules, prices, platform capabilities and market access. For regulatory opportunities, check scope, jurisdiction, commencement and required actions separately. The existence of a rule does not prove that buyers need the proposed product.

For asset sales, identify the likely acquirer and the work or commercial value they gain. Interest from end users in an advertised service does not establish an operator's willingness to buy the brand or website.

### Screening rule

Reject candidates that violate a firm constraint or have a demonstrated fatal dependency. Keep a promising candidate with a material unknown as a research or test candidate. Do not require unsupported assumptions to be marked as passing.

Compare demand, customer access, delivery feasibility, time to cash, capital exposure, owner workload, financial return and transferability where relevant. Recurring revenue, AI use and low capital needs are preferences unless explicitly required.

Remove an option that is no better on the important dimensions and clearly worse on one, unless it offers a specific benefit the user values. Avoid numerical scores whose weights conceal the actual tradeoff.

## 6 Design complete alternatives

Each serious candidate gets the same compact profile. The profile must support its financial calculations.

### Commercial and operating plan

Name the initial users and intended outcome. For a commercial option, identify the paying segment and paid outcome, and distinguish the payer, user and asset buyer. A marketplace must identify both sides and which side funds it. Media may have readers and advertisers with different needs.

Define the offer, scope, price basis, purchase process and customer promise. Explain why a buyer would switch from the current alternative. Record renewal, repeat purchase or retention requirements when relevant.

Map the delivery steps and assign each to the owner, team, partner, customer, software or AI. Compare people, ordinary software and AI for the tasks where the choice matters. Identify the required competence and the consequence of error. Use that assessment to set review needs. A category label alone does not determine them.

### Development plan

Screen these methods before selecting one:

- Transfer or package existing assets with limited new development.

- Use existing products and configure standard tools.

- License, resell or adapt an existing product.

- Commission a defined product or set of assets from a supplier.

- Build custom software or production assets.

For credible methods, compare time, initial cash, recurring cost, quality, ownership and handover needs. Examine the strongest alternative method when it could change the choice. Avoid research into minor implementation details that cannot change the outcome.

For each serious candidate, outline its initial repository: purpose, specifications, instructions, starting assets, first work units and applicable checks. Compare reuse of an existing foundation, configuration and custom development where the choice changes cost or capability. Estimate repository bootstrap cash and owner hours separately from the remaining development and commercial launch work. Count each cost once in the financial model. Fully specify the selected route's bootstrap; execute it when project setup is requested.

Name the first complete commercial deliverable. It could be a transferable brand package, a paid service outcome, a publication, a working product or a physical order. Define what the customer can actually receive and use.

Distinguish launch work from later improvements. Make each later development conditional on evidence. A move from service delivery to software must have its own customer case, cost and support model.

### Marketing and sales plan

Screen direct sales and outreach, search demand, publishing and community, paid promotion, platform distribution, partnerships and referrals, and offline channels. Select a primary route and compare the strongest credible alternative.

For the selected route, record the audience, offer, message, channel, call to action, purchase steps, cost, owner hours and expected delay. State why this route reaches the payer.

Use a funnel appropriate to the model. Examples include visits to paid orders, target accounts to signed contracts, accepted enquiries to commission, or buyer conversations to completed asset transfers.

State the denominator and period for each rate. Free signups, enquiries, qualified opportunities and paying customers are different outcomes. Include acquisition work even when the owner performs it without an immediate cash payment.

For a test, specify the claim being tested, sample, spend cap, duration and decision threshold in advance. Derive the threshold from the economics. A few favourable responses can support interest without proving repeatable sales or retention.

### Funding and ownership

Compare self funding, customer funded delivery or deposits, reinvested trading income, and a partner who contributes capital or delivery capacity. Include debt or external equity when relevant. Record funding separately from repository bootstrap.

For each viable funding route, show when cash arrives, what must be delivered, refund exposure, retained ownership and future payments. Customer deposits carry delivery obligations. A partner's labour or capital has a cost through payment, profit share, control or ownership.

Do not present borrowing or investment as earned income. Do not assume grants, customer deposits or partnership commitments are available without evidence.

### Launch specification

For each serious alternative, specify the work and funding needed to reach its first intended outcome. A commercial route uses `docs/commercial-launch-spec.md` through the first commercial outcome. An explicitly noncommercial route uses `docs/launch-spec.md` through the first useful operational outcome. Carry the selected specification into the initial repository, linking its costs to the financial model and delivery requirements to the operating model.

| Milestone | Required plan |
| --- | --- |
| Resolve the main uncertainty | Name the claim, test, expected evidence, spend limit, owner hours and decision date. |
| Prepare the deliverable | Define the offer, assets, delivery process, dependencies, responsibilities and acceptance checks. |
| Reach the first intended outcome | Specify distribution or sales and what counts: payment and delivery, licence start, accepted referral, asset transfer, or the agreed operational outcome. |
| Decide the next commitment | Compare actual costs and results with the case study. Continue, change, sell, pause or stop against stated thresholds. |

For each milestone, assign an owner, dependencies, duration, cash budget, hours, output and acceptance evidence. State what happens if the threshold is missed. Use actual dependencies to set dates; do not force every model into the same 30 or 90 day launch schedule.

For an asset sale, define exactly what transfers and what continuing support is included. For an operating business, define the first delivery cycle and how it can repeat within the cost model. For a partnership, establish ownership, responsibilities and payment terms before dependent work.

Specify when funding becomes available, the cash required before receipts, and the obligations attached to deposits, debt or partners. Keep repository setup, later production, customer acquisition and delivery costs identifiable. The launch specification is complete when the work is defined; record commercial outcomes only after they occur.

Use the existing Business Building OS concepts for the selected route: framing, economics, offer and customer acquisition, commercial delivery, learning, reliable operations and the next decision. Keep a service or publication in that form when its economics justify it. Greater automation and a software product remain separate decisions.

## 7 Model potential financial gains

### Common comparison basis

Use the same starting date, reporting currency and horizons for every candidate. Use dated cash events for one-off asset sales. Model the first year monthly for recurring operations, or seasonally where that better represents the business. Keep enough detail to expose payment delays, stock purchases, renewals and funding gaps. Do not create monthly detail that has no effect on the decision.

Show downside, central and upside cases. The central case is an explicit set of planning assumptions, not a prediction. Include a plausible failure or no sale case. Change the underlying drivers rather than applying an arbitrary percentage to the final result.

Use future costs from the decision date. Record historical acquisition and development spending separately. Do not charge those sunk costs again to one candidate. When comparing against an asset sale, do not subtract the same forgone sale value a second time.

Default to figures before personal tax. State which business taxes are included. Exclude taxes collected for others from revenue. Use current exchange rates and state their date when converting currencies.

Show nominal cash totals first. When payment timing could change the ranking, also discount future cash to today's value using an explicit rate or rate range. Apply the same basis to all options. If returns on early sale proceeds are included, state that assumption separately.

### Financial outputs

| Measure | What to report |
| --- | --- |
| Revenue | Sales earned during the period. Keep orders, invoices and cash receipts distinct. |
| Cash after business costs | Customer cash received less setup, development, acquisition, delivery and ongoing cash costs. State the treatment of owner pay. |
| Owner economic result | The owner's attributable financial result after charging owner time once. |
| Initial and peak funding | Cash required to start and the greatest cumulative funding gap before financing. |
| Time to cash | First customer payment or asset sale, with its evidence basis. |
| Break even and payback | Volume needed to cover costs and when initial cash is recovered. |
| Owner workload | Launch hours, ongoing hours and peak delivery or support demand. |
| Sale proceeds | Conditional proceeds after sale costs, obligations and ownership shares. |
| No sale outcome | Cash spent or earned, hours used, commitments remaining and assets still held. |
| Retained value | Any unsold asset value, shown separately from cash and supported by suitable evidence. |

For a simple wholly owned case without borrowing, show cash before owner pay and subtract owner hours at an explicit hourly value. If owner salary is already in the cash costs, add it back for this comparison before charging the same labour. Keep actual salary payments in the bank cash schedule. Test a range of hourly values when the opportunity cost is unknown.

For partners, debt or outside equity, use a separate owner cash ledger. Calculate actual salary, distributions, sale receipts and other cash returned to that owner. Subtract the owner's contributions, directly paid costs and time cost. Include payment priorities, repayments, profit shares and dilution. Show undistributed company cash separately. Do not estimate personal gain by multiplying cash before owner pay by an ownership percentage.

### Core calculations

Use these calculations with consistent definitions and periods:

```text
Contribution per unit = net unit price - variable cost per unit

Break even units = fixed costs / contribution per unit

Cash CAC = acquisition cash spending / new paying customers acquired

Full CAC = (acquisition cash spending + unpaid acquisition time cost)
           / new paying customers acquired

Owner time cost = total owner hours × selected hourly value

Result after owner time for a wholly owned project
  = project cash surplus before owner pay - owner time cost

Peak funding gap = max(0, -lowest cumulative project cash balance)
```

For break even, contribution must be positive. Use compatible periods and include step changes in staffing or capacity. For CAC, match acquisition spending to the customers it produces. A zero customer count means CAC is not yet measurable. Do not subtract CAC again when the same spending is already in the cash forecast.

Use Full CAC to assess acquisition efficiency. Do not also charge its owner time component as a business cost when those hours are included in total owner time.

Calculate the funding gap before adding loans, investments or owner funding. Show an additional reserve separately when the business needs one. Check customer deposits against delivery and refund commitments.

### Use the drivers of the model

| Model | Revenue and capacity drivers |
| --- | --- |
| Domain or package sale | Credible buyer pool, offer, sale timing, fees, build cost, selling effort and unsold outcome. |
| Licence | Licence fee, occupied periods, operator renewal, defaults, support and asset condition. |
| Services | Qualified opportunities, wins, delivery price, jobs per period, utilisation, revisions and delivery hours. |
| Software or recurring information | New paid customers, activation, retention, price, usage costs, support and renewals. |
| Lead generation or brokerage | Acquisition volume, qualification, accepted outcomes, completed transactions, fees and refund or rejection rates. |
| Marketplace | Both sides' acquisition, available supply, completed transaction volume, take rate, incentives and fulfilment of transactions. |
| Media and education | Reachable audience, engagement, paid conversion, retention, sponsor demand and production cost. |
| Physical goods | Units sold, landed cost, inventory purchases, shipping, returns, stock loss, payment timing and repeat orders. |

Build demand from reachable customers and channel capacity. Do not take an arbitrary share of a large market and call it revenue. Limit sales by delivery capacity, supply and time to fulfil them.

Model recurring customers as groups acquired in each period and retained over later periods. A lifetime value estimate must use contribution after delivery costs. If retention is untested, show finite retention scenarios. Do not infer a long customer lifetime from a short trial or use revenue alone to claim acquisition payback.

For AI or automation, show a cost bridge from the initial process to the proposed mature process. Include data access, licences, compute, review, exceptions, rework, support and maintenance. Cost reductions require measured changes or explicit assumptions. Neither automation nor greater volume establishes a lower total cost by itself.

### Sale and retained business outcomes

Show an operating outcome and a sale outcome separately when both matter.

In a sale scenario, count operating cash separately only when the seller retains it. If accumulated cash transfers to the buyer and is included in the sale consideration, do not add it again. Stop counting the sold business's subsequent cash as the seller's income. Include only sale payments received within the reporting horizon under the stated scenario. Show later or unpaid amounts separately, including conditional earnouts.

In a retained business scenario, show operating cash through the horizon. Show any estimated business value at that horizon separately. Do not add that value to cash already received and describe the total as realised earnings.

Use comparable completed sales where available. Record asset type, scale, profit basis, timing and material differences. Marketplace asking limits and advertised prices are not achieved values. Profit multiples for established businesses do not value an unproven marketing website.

If sale likelihood cannot be supported, report sold and unsold cases without assigning percentages. Calculate expected value only with explicit, defensible probabilities for mutually exclusive outcomes. Show how the recommendation changes when those probabilities change.

### Sensitivity and decision thresholds

Identify the few assumptions that can change the ranking. Calculate the relevant thresholds: minimum sale price, maximum build hours, maximum acquisition cost, required retention, number of customers, delivery time per job or sale probability needed to beat the baseline.

Test a coherent adverse combination as well as changing one variable at a time. For example, slower sales can increase both holding costs and owner work. Do not assume all favourable inputs occur together.

### Worked financial illustration

All inputs in this illustration are invented. They demonstrate the calculations and how a decision can change. They are not domain valuations, market benchmarks or forecasts. Amounts are nominal GBP before tax and financing. Each route assumes full ownership and cash costs before owner pay. Retained asset value and interest income are excluded.

The domain case assumes an available £2,000 offer, a 10% selling cost and two owner hours. The package case assumes a £12,000 sale in month 6, a 10% selling cost, £1,600 of build and marketing costs, £10 monthly holding costs until sale, and 80 owner hours.

The service charges £600 per client per month. It has no clients in months 1–3, two in months 4–6, four in months 7–12, and six in months 13–36. This gives 174 paid client months. It acquires 18 customers at £150 each, including 12 replacements. Two customers are acquired in each of months 4, 7, 9, 12, 13, 15, 21, 27 and 33. Replacement customers keep active totals unchanged in the relevant months.

Service cash costs are £150 per paid client month, £1,200 upfront and £100 per month, plus acquisition costs. Owner work is 60 setup hours, three hours per month for selling and administration, and four hours per paid client month. These quantities are assumptions to challenge in a real case.

| Conditional route | Cash after costs at 12 months | Cash after costs at 36 months | Owner hours over 36 months | 36 month result after owner time at £50 per hour |
| --- | ---: | ---: | ---: | ---: |
| Sell the domain | £1,800 | £1,800 | 2 | £1,700 |
| Sell the package in month 6 | £9,140 | £9,140 | 80 | £5,140 |
| Operate the service | £9,900 | £70,800 | 864 | £27,600 |
| Package remains unsold | −£1,720 | −£1,960 | 80 | −£5,960 |

The unsold case assumes no further owner work beyond the stated 80 hours. The domain and package remain owned, but their value is unknown.

At 12 months and £50 per owner hour, the service result is −£900 after its 216 owner hours. The package sale leads. At 36 months and £50 per hour, the service leads. At £80 per hour over 36 months, the package leads: its result is £2,740, against £1,680 for the service and £1,640 for the domain sale.

The package needs £1,660 before its assumed sale. The service needs £1,900 under a payment sequence in which fixed and acquisition costs precede the month's customer receipts. Delivery costs follow those receipts. The service recovers its initial cash in month 6.

With these assumptions, the package needs a gross sale price above £8,177.78 in month 6 to beat the domain sale after charging owner time at £50 per hour. This is a decision threshold, not a prediction that a buyer will pay it. The unsold branch shows why the conditional package result cannot be presented as an expected return.

## 8 Challenge and recommend

Review the preferred candidate and its strongest alternative using the same evidence standard. A reviewer or separate analysis pass should check:

- Whether the options have distinct commercial outcomes and comparable detail.

- Whether source claims, assumptions and calculations are clearly separated.

- Whether the model includes acquisition effort, delivery capacity and ongoing costs.

- Whether future sale proceeds, recurring income or owner labour are counted twice.

- Whether a cheaper development method or different buyer changes the result.

- Whether the recommendation survives the main adverse assumptions.

Recommend one complete route. Explain the advantage in money, time and risk. Present one alternative and the condition under which it becomes preferable. Do not merge all attractive features into a larger new project.

Choose a route that the evidence supports: sell, licence, operate, use within an existing business, hold until a named review point, or stop and release the asset. All candidates can be rejected.

Keep the preferred business route separate from its next test. Where a critical assumption is unresolved, name the provisional route and the bounded test needed before further commitment. If no route leads, identify the two competing routes and the specific uncertainty that prevents selection. State the evidence needed to commit further cash or owner time.

## 9 Bootstrap the initial GitHub repository

The bootstrap produces the initial repository from which the selected project can begin. It contains a project-specific bootstrap process, the specifications needed to direct work, and the starting material justified by the operating model. Define the boundary of this initial repository in advance. Later product development, commercial launch and operations remain stages to execute.

This adapts the [Production Skills bootstrap guide](https://github.com/sb-dev/production-skills/blob/ae4c0f1bd63107f9dc33e192bbf2a02a9cab75cf/docs/bootstrap/README.md) and [new-project process](https://github.com/sb-dev/production-skills/blob/ae4c0f1bd63107f9dc33e192bbf2a02a9cab75cf/docs/bootstrap/new-project-process.md). Reuse the small initial workspace, durable research records, custom stages, explicit outputs and verification. The case study supplies the commercial decision; review and reuse its evidence before commissioning further research.

### Adapted bootstrap process

| Stage | Work and completion evidence |
| --- | --- |
| 0 Create the workspace | Create or use the selected GitHub repository. Begin with a minimal `README.md` and `docs/research-logs/README.md`. Record its purpose and preserve any existing project work. This is the durable workspace. |
| 1 Write the custom bootstrap | Save `docs/research-logs/YYYY-MM-DD-<project>-bootstrap.md`. Identify the chosen model, accepted case study, initial repository scope, required stages, starting contents, budget and completion checks. |
| 2 Ground the operation | Review existing evidence about the actual work. Where gaps matter, select and access sources, examine them, then challenge the findings. Persist methods, limitations and decisions before dependent design work. |
| 3 Choose the foundation | Derive the customer delivery and internal workflow. Assess existing tools, templates, services, code and relevant skills for reuse or adaptation. Justify custom work, ownership, recurring cost and maintenance. |
| 4 Specify the project | Define the operating model, initial repository contents and first development tasks. Add the appropriate launch specification. Give each required output an owner, dependency and acceptance condition. |
| 5 Populate the initial repository | Create the agreed specifications, instructions, starting assets and useful code or configuration. Add checks that apply to those contents. Record later implementation as planned work. |
| 6 Verify and hand over | Check navigation, instructions, required files and any claimed runnable behaviour. Record actual results, remaining limitations, the GitHub reference and the next executable work unit. Read back the resulting repository state. |

Each stage records its purpose, inputs, work, decisions, provisional claims, outputs and exit criteria. Save substantive evidence in the repository and commit completed stage work before dependent stages proceed. A written stage description records intended work; completing the stage requires its stated evidence.

The research scope follows the knowledge and consequences of the selected business. Where substantive new research is needed, source selection, direct examination and independent challenge become separate tasks with their own records and exit criteria. The source project's exact five-book corpus, six-specification structure, fifteen examples and Extension Packs are requirements for its Production Skills products. This business workflow selects the research depth and specification set for the commercial model. If the chosen project itself produces a Production Skills product, apply the relevant family contracts. See the [domain research process](https://github.com/sb-dev/production-skills/blob/ae4c0f1bd63107f9dc33e192bbf2a02a9cab75cf/docs/bootstrap/domain-research-process.md).

Add development, marketing, data, rights or testing specifications where they need distinct contracts. Keep calculations linked to their authoritative model. Populate only directories that contain useful starting material. Store each substantive decision once and reference it from the files that use it.

### Contents selected by operating model

These are starting profiles. Adapt them to the actual offer, delivery method and sales route.

### Completion and financial treatment

The bootstrap is complete when the agreed starting repository exists, its instructions match its contents, applicable checks have actual results, and the next work unit can begin from the recorded material. If its agreed scope includes runnable code, verify that code from a clean checkout. A sample workflow verifies the starting material; customer demand and successful paid delivery require their own evidence.

Report repository setup cash and owner hours, remaining launch funding and work, and the costs of operation separately. Include them once in the case study's financial comparison. Repository creation or build cost does not establish a higher resale value; any proposed premium still needs a buyer case.

If the recommendation is to make no new commitment, pause or close the case, record that decision. Holding or releasing a domain are also valid outcomes when applicable. Create a repository only for an agreed project scope, and record its observed state. The commercial launch specification defines subsequent work and its commitment points.

## 10 Case study output

Produce one report with the following sections. Keep the recommendation first and supporting detail available beneath it.

1. **Recommendation.** Preferred route, one alternative, expected commitment and the conditions that change the choice.

2. **Starting position.** Supplied domain, idea, description or specifications; input origins and revisions; objective, requirements, constraints, assets, baseline and evidence status.

3. **Option coverage.** Families considered, candidates retained and reasons for exclusions.

4. **Complete alternatives.** Commercial, operating, development, marketing, funding and ownership plans, with repository bootstrap outlines and commercial launch specifications.

5. **Financial comparison.** The same horizons, downside/central/upside cases, no sale outcomes, owner time and sensitivity thresholds.

6. **Repository bootstrap.** The selected route's initial contents, applicable instructions and skills, custom staged process, setup costs and hours, launch specification, first work units and completion checks. After execution, include the verified GitHub reference and observed results.

7. **Evidence and open questions.** Sources, assumptions, calculations and the next evidence that matters.

Include one compact comparison table for the serious alternatives. Its columns should show first cash, peak funding, 12 and 36 month cash, owner hours, owner economic result and the decisive uncertainty. Put detailed scenarios below the table.

Record the research date and material revisions. Update the affected inputs and recommendation when new offers, customer results, costs or rules arrive. Preserve the prior decision and why it changed. Distinguish case study completion, repository bootstrap completion and achieved commercial outcomes.

### Examples of evidence that changes a case

The Martyn's Law example in Business Building examples v2, page 1, proposes a tracker for 100+ capacity venues. Current SIA guidance normally uses 200 or more people reasonably expected to be present for premises, alongside other scope conditions. It states that commencement is expected in spring 2027, with the exact date to be confirmed. The case must therefore check the target group, urgency and required paid work before forecasting revenue. [SIA guidance](https://www.gov.uk/guidance/understanding-martyns-law-and-the-sias-role-as-regulator).

The subject access request example on page 3 uses a 30 day statutory limit. ICO guidance uses one month, with defined timing and extension rules. That difference changes deadline logic and delivery requirements. It does not by itself invalidate a processing service. [ICO guidance](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/right-of-access/what-should-we-consider-when-responding-to-a-request/).

These are focused checks, not a market validation of the 54 examples.

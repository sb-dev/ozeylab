# Run an ozeylab example

The 15 guides are designed exercises. Their briefs are synthetic. They have not been run as complete researched cases or target bootstraps. Existing financial fixtures demonstrate arithmetic only.

## Workspace and setup

Use a disposable clone or worktree with Node.js 24 and a coding agent. Run commands from its root. Install the repository-local skills using the root README. Keep the example source files unchanged. Do not mix exercise projects with a real portfolio or publish their records as real opportunities.

Each guide gives a stable `example-lN-NN` project ID and an intake command. Run it once. If that ID already exists, inspect and resume its record instead of creating another. The portfolio-query exercise is read-only and creates no project.

## Evidence and effort

Read the guide's brief before its prompt. Currency amounts, capacity limits and fictional clients are exercise inputs. They do not establish market demand, current prices, ownership or legal clearance. Register the brief as a source; distinguish its claims from observed evidence and calculations.

Use current primary sources for facts that can change. Preserve URLs, versions, examination dates and extraction gaps. Do not invent interviews, domain checks, quotations, agreements or customer results. Failed source access remains an explicit limit.

For each run, record the input and process revisions, actual runner/model settings, output paths and checks in the project's maintenance log. Do not guess model identity. Limit initial case research to 12 search queries and 30 source reads. Reserve effort for review. If those bounds are insufficient, report the missing evidence and proposed next investigation. A limit does not make the case complete. Use only already-authorised access; these exercises do not authorise spending, purchases, messages or publication.

## Case completion and review

Use the canonical skill processes and the checked-in case-study workflow. Screen all six operating families. Keep a relevant baseline, complete serious alternatives, justified financial drivers and a conditional recommendation. No new commitment is a valid recommendation.

For quantitative cases, use the same decision date, GBP and 90/365/1095-day horizons unless a different basis is explained. Include downside, central and upside scenarios; add no sale when relevant. Keep unknown values unknown. State all synthetic assumptions and charge owner time once.

Obtain a separate read-only review for material assessments and ontology changes. Use `templates/review.md` with the actual assessment and input revision. Resolve findings before recording `pass` or moving to `assessed`. If no separate reviewer is available, leave the review outstanding and the lifecycle state unchanged. A producer self-check is not independent review.

Run `finance` when models change, project validation, index generation and `npm run check` after a coherent update. These checks assess structure, references and calculations. Inspect the guide's specific acceptance criteria separately. Query-only work must leave files unchanged.

## Level 3 accepted selection

Each bootstrap guide is a standalone exercise with a proposed route. Before bootstrap:

1. Create and assess its case from the supplied brief, including the alternative comparison and independent review.
2. Obtain an explicit selection for the exercise. Record its option, assessment, decision and agreed starting scope. The guide does not pre-approve a real business.
3. Accept the coherent case and selection on the disposable checkout's default branch under repository commit rules. Record the full accepted commit. An unmerged proposal is not the accepted basis.
4. Resolve a target directory outside ozeylab. For a full GitHub handover, also resolve the authorised owner/name, visibility and repository-creation scope. Use existing authorisation when it covers those details.

The bootstrap skill supplies these resolved values to the documented CLI command. Never invent an accepted SHA or copy a synthetic `pass` record to bypass the gates. If the route is not selected, complete the proposal and state the missing decision.

## GitHub handover rule

Run the selected profile's acceptance exercise and the agreed starting behaviour. A generated scaffold remains planned until its stages are performed.

If the user has authorised the target, create or update it, read back the exact remote commit and contents, and record the two-way central/target references and verification. Only then may the central record become `bootstrapped`. If there is no authorised target, finish and check the local starting assets, report “local preparation only”, and leave the project below `bootstrapped`.

The target owns current execution specifications. The central case keeps the comparative decision and a historical accepted basis. A sample delivery, local export or synthetic transaction does not prove a commercial outcome.
